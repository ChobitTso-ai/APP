# Claude ↔ CODEX 交班規則

有些工作（目前是插圖繪製）交給 CODEX 做。**CODEX 不碰 git**，
檔案由 Dr.Tso 用 GitHub 網頁搬運。這份文件定義兩邊的邊界與交接方式，
免得同一批檔案被兩邊互改。

## 流程

```
Claude 寫規格書  →  docs/handoff/*-spec.md  （進 repo，版本控管）
       ↓ Dr.Tso 把規格貼進 CODEX 對話
CODEX 產出檔案   →  本機專案資料夾
       ↓ Dr.Tso 把整批壓成 zip 交給 Claude（丟進對話或傳到 repo，見下方「怎麼把檔案交給 Claude」）
Claude 整合      →  驗收、接進 App、跑測試、commit、push、開 PR、合併
```

圖已經上線之後要修改，走下方「修改已上線的圖」。

**Claude 讀不到本機磁碟。** 這個 repo 的 Claude session 跑在雲端容器裡，
只有一份 GitHub clone，看不到 Windows 的 `D:\…\Local project\…`。
本機那邊的檔案（AGENTS.md、HANDOFF.md 等）要讓 Claude 看到，
只能貼進對話或上傳到 repo。

## 分工邊界（最重要，違反就會衝突）

| | Claude | CODEX |
|---|---|---|
| 規格書 `docs/handoff/` | 寫 | 讀 |
| 素材檔（`.svg` 等） | 讀、驗收、必要時微調 | 產出 |
| App 程式碼（`index.html`／`app.js`／`styles.css`／`tests/`） | 改 | **不要碰** |
| git（commit／push／PR／合併） | 全部 | **不要碰** |

CODEX 只負責產檔案，不要順手幫忙改程式碼或動 git——Claude 同時在改同一批
檔案，動到就會衝突。

## 規格書的寫法

- 一個工作一份，放 `docs/handoff/<主題>-spec.md`。
- 內容要能**獨立閱讀**：CODEX 每次都是從零開始，看不到這邊的對話。
- 一定要寫「完成前自我檢查」段落，列出可以用 grep／ls 驗證的硬條件，
  否則交回來的東西很難一次到位。
- 規格改了就改規格書本身，不要只在對話裡講——下次重產會用回舊規格。

## 怎麼把檔案交給 Claude（2026-09-24 實測，09-30 補）

**`.svg` 單檔傳不上去**——對話上傳與 GitHub 網頁 Upload files 兩邊都失敗
（SVG 可以夾帶 script，上傳驗證多半直接拒收）。**包成 zip 就過得去**。實測可行的順序：

| # | 做法 | 實測 |
|---|---|---|
| 1 | **整批打包成 `.zip` 丟進對話** | ✅ **可行，首選。**Claude 解開後自己放進 repo 並 commit |
| 2 | 把 `.zip` 傳到 repo 的 `assets/dx/` 或 `assets/care/`（GitHub 網頁進到該資料夾 → Add file → Upload files） | ✅ 可行（2026-09-28、09-30 共三次）。Claude 解開後會把 zip 刪掉 |
| 3 | GitHub **Create new file**（不是 Upload）→ 檔名自己打、內容貼進去 | 未實測，但不經過上傳機制，理論上可行 |
| 4 | 把 SVG 原始碼直接貼進對話 | 可行，但一次只適合一兩張 |

zip 直達做法：把該批 `.svg` 全選 → 右鍵 → 壓縮 → 丟進對話即可。
zip 檔名隨意（中文也可以），不用先分資料夾，Claude 會依檔名判斷該放 `dx/` 還是 `care/`。

- 檔名必須與規格書完全一致，程式是照檔名找檔的。
- **有版權的參考資料不要上傳**：本 repo 是 public，commit 之後即使刪除，
  git 歷史裡仍然留著。參考圖請直接貼在 CODEX 對話裡。

### 依情況分工

| 要做的事 | Dr.Tso | Claude | App 程式要改嗎 |
|---|---|---|---|
| 修改現有的圖（最常見） | 請 CODEX 改好、檔名不變，壓 zip 交來 | 驗收、做新舊對照、跑測試、合併 | 不用 |
| 新增一張圖 | 說明要放在哪個畫面、哪個選項；CODEX 畫好壓 zip 交來 | 先把檔名與內容補進規格書的檔案清單，再接進 App | 要（Claude 改） |
| 換位置、刪除、改檔名 | 直接跟 Claude 說 | 改資料檔（`data/*.js` 的 `img` 欄位）與測試 | 要（Claude 改） |
| App 圖示 | 請 CODEX 改 `icon-master.svg` | 重新轉出各尺寸 PNG 圖示 | 不用 |

規則本身要改（某個顏色代表什麼、取景方式）時，先改規格書，
理由見上面「規格書的寫法」最後一條。

### 從哪一版開始改

repo 裡的圖就是 CODEX 最後交來的原檔：2026-09-30 把 git 歷史裡三個交件 zip
逐檔比對過，31 張與 repo 版**逐位元組相同**，Claude 沒有在 repo 端改過任何一張
（v1.5 那 6 張牙冠折斷族有變動，是換上 CODEX 第二批重畫的版本）。
所以 CODEX 直接改它本機那份即可——前提是它本機那份就是最後交出來的版本。

**Claude 之後若在 repo 端微調了某張圖，要記在下表。**CODEX 改那張時，
要先從 GitHub 下載 repo 版當底稿，不然會把微調蓋掉。

| 檔名 | Claude 改了什麼 | 日期 |
|---|---|---|
| （目前沒有） | | |

### 給 CODEX 的指令（範本）

```
請依規格書 dental-trauma-art-spec.md 修改下列插圖：
・fx-enamel.svg：（要改的地方）
・lux-lateral.svg：（要改的地方）

規則：
1. 檔名、viewBox 都不變；只交有改的檔案
2. 照規格書「完成前自我檢查」跑一遍再交
3. 不要改程式碼、不要動 git
4. 改好的檔案壓成一個 zip 給我
```

新開的 CODEX 對話看不到之前的內容，要先把規格書整份貼給它。

### Claude 收到後做的事

1. 解開 zip，確認每個檔名都在規格書的檔案清單裡。
   檔名差一個字（大小寫、連字號）不會報錯，只會變成一張沒人用的新檔，舊圖原封不動。
2. 跑規格書「完成前自我檢查」的硬條件：viewBox、無 `<text>`、無 `id`、
   無 base64／`<style>`／`<image>`、`data-part` 齊全、每檔 < 60KB。
3. 照 App 實際尺寸做新舊並排對照圖給 Dr.Tso：診斷頁大圖、決策樹選項縮圖（72×92）、
   查閱卡片（74×96）、決策樹總覽（30×38）。Claude 看技術條件與縮小後認不認得出來；
   **解剖與臨床畫法對不對，由 Dr.Tso 判斷。**
4. 跑 `./tests/run.sh`，其中「每張圖都載得到」「`assets/` 底下每一張圖都有被程式碼引用」
   兩項會抓到檔名拼錯或漏接。
5. Dr.Tso 說「合併吧」→ 合併、確認部署。Dr.Tso 事先說免看對照圖的話，驗收通過就直接合併。

上線後手機若還看到舊圖，重新整理一次；加到主畫面的 App 連網打開就會換新
（`sw.js` 是 network-first，線上一律先拿最新版）。
